# Agent Harness 架构设计题

每个模块选择一题。以下是设计取舍，不是性能实测结论；其中提到的长期记忆、事件队列和异步调度属于扩展方案，不代表本仓库已经实现。协议资料核对日期：2026-11-04。

## 模块一 · 第 2 题：200 轮对话如何压缩并保持流畅？

压缩的单位应是**完整交互**，而不是任意条消息。一次工具调用及其结果必须一起保留或一起移出活动上下文，否则会留下没有结果的调用，既破坏协议，也改变语义。

我会把上下文分为三层：原始记录持久化；工作摘要保存当前目标、约束、用户更正、已确认事实、未完成事项及来源；最近几轮完整保留，用于理解“它”“继续刚才那个”等追问。待办等业务状态放在结构化存储中，不把摘要当数据库。

每次模型请求前预算 system、工具 Schema、历史、当前输入和预留输出的总量，接近阈值就压缩最旧的完整交互。摘要记录事实的时间与消息 ID，明确区分“用户说过”“工具证实”“尚待验证”；大工具结果保留关键字段与原文位置。摘要是历史数据，不能提升成新的系统指令。

连续摘要会积累误差，因此保留原文；发现矛盾或用户追问旧细节时回查原始记录。用户的新更正覆盖旧结论，但留下更正关系。压缩失败时保留最近完整交互，并明确标记早期细节未进入上下文；不能把被截断的信息当成已经记住。

验收不用“摘要读起来不错”，而用压缩前后的同一组问题：早期约束、最新更正、代词指代、工具返回的 ID、未完成事项，以及未知事实能否承认不知道。还要检查工具调用配对和上下文上限。本 MVP 采用基础摘要与近期完整交互；完整历史保留在 SQLite，未实现语义检索。

## 模块二 · 第 1 题：半个月后再次提问，怎样召回 memory？

先判断问题依赖哪类历史：一般知识未必需要记忆；“上次那个方案”需要检索会话事件；个人偏好适合读取已确认事实。不能看到相似问题就复制旧答案，价格、天气、计划状态等信息可能已经过期。

我的召回链路是：先按用户身份与允许的会话范围过滤，再用关键词和语义检索找候选，按相关性、时间、可信度和是否已被更正重排，最后读原始片段核验。权限过滤必须发生在检索时，不能等其他用户的数据进入模型后再要求它保密。

将少量证据连同来源、时间、适用范围放入独立的历史资料区，位于近期对话之前；它们用于辅助回答，不作为指令。涉及动态事实时重新调用工具。存在冲突就解释差异，无法定位“上次”具体指哪一次才向用户澄清。

写入记忆也要筛选：显式偏好、用户确认的事实、决策和结果值得保留；模型猜测与失败工具结果不能直接变成事实。支持更正、删除和过期，而不是只追加。评估看正确历史命中率、过期答案使用率和跨用户泄漏，不只看向量相似度。本 MVP 只做 session 内的历史恢复和 todo 状态读取，不默认跨窗口共享记忆。

## 模块三 · 第 1 题：长任务执行中忘记目标怎么办？

把目标从聊天文本中提取成持久化任务记录：目标、约束、验收条件、当前步骤、已完成证据、阻塞点。只有用户指令或明确的需求更正可以改变目标；网页或工具输出不能偷偷扩大任务范围。

每轮模型调用重新提供精简的任务状态；工具完成后根据实际结果更新检查点。完成某一步必须有对应证据，例如文件变更和测试结果，不能只相信模型说“完成了”。最终结束前逐条核对验收条件，并区分成功、部分完成、失败和等待输入。

几种方案的取舍：反复注入目标简单便宜，但容易重复且缺少执行记忆；计划加检查点可恢复且便于审计，但需要处理计划过时；独立检查者能发现偏航，却增加调用成本，而且可能与执行者犯同样的错；拆分子任务能限制局部上下文，但会引入依赖和合并成本。

我会先选“持久化目标 + 小步检查点 + 关键节点复核”，只在失败或需求改变时重规划，并设轮次、时间和费用预算。预算耗尽要保留进度并报告剩余工作，不能伪装成成功。本 MVP 用 todo 演示持久状态，并限制每次请求的循环次数；没有实现完整长任务编排器。

## 模块四 · 第 2 题：busy 时新消息和异步结果同时到达？

生产方案采用**每个 session 一个串行状态写入者**：入口先把事件持久化到 inbox，再返回接收凭证。事件包含 event_id、session_id、run_id、类型和序号；工具结果额外携带 tool_call_id。短事务只负责入队和状态变更，不跨网络请求持有数据库锁。

新消息默认排队；明确的“停止”优先触发取消标记，在安全检查点停下。取消不能撤销已经发生的外部副作用，因此结果仍需登记，并向用户说明实际完成了什么。用户修改目标时增加运行版本，旧运行返回的模型输出不能覆盖新版本。

工具完成事件按调用 ID 匹配并去重；重复通知不重复写状态，未知调用隔离排查。取消后的迟到结果仍记录执行事实，但不自动恢复旧任务。独立任务的结果通知可以发送给用户；依赖该结果的任务才恢复对应执行流。持久化结果与待发送通知采用同一事务中的 outbox，消费者重试时按 ID 去重。

需要保持的约束是：同一会话只有一个状态修改者；每个调用只有一个已接受的终态；事件重放不重复触发业务副作用。外部工具必须自己支持幂等键或结果对账，队列去重并不等于“副作用恰好一次”。

本 MVP 的三个工具均同步执行，采用更小的策略：同一 session busy 时拒绝新请求且不改历史，不同 session 独立。这里的 inbox/outbox 和异步通知仅为扩展设计。

## 模块五 · 第 1 题：Claude Code 与 OpenAI-compatible 工具输出有何区别？

首先需要区分层次：Claude Code 是管理上下文、执行工具的应用与 harness；function calling 是模型和应用之间的协议。终端显示的进度或工具结果，不等于 API 原始消息。Claude Code 官方介绍确认了这一分层；未公开的内部实现不作推断。[Claude Code 工作原理](https://code.claude.com/docs/en/how-claude-code-works)

比较公开的客户端工具协议，更准确：

| 维度 | Anthropic Messages | OpenAI-compatible Chat Completions |
| --- | --- | --- |
| 发起调用 | assistant 的 `content` 中包含 `tool_use` 块，`input` 为对象 | assistant 的 `tool_calls` 数组中包含函数信息，`arguments` 为 JSON 字符串 |
| 返回结果 | 下一条 user 消息中的 `tool_result`，用 `tool_use_id` 关联 | `role: tool` 消息，用 `tool_call_id` 关联 |
| 错误表达 | `tool_result.is_error` 有专门字段 | 通常在工具结果内容中约定错误对象 |

以上分别见 [Anthropic 工具结果格式](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[智谱工具调用](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)与[火山方舟 Function Calling](https://docs.volcengine.com/docs/ark/function-calling?lang=zh)。GLM 和豆包的具体模型、接口版本对强制调用、思考内容和并行调用的支持要逐项核对，不能只凭“兼容”假定完全一致。

从实现角度判断，内容块适合在一条消息内表达文本、调用及多模态结果，但解析器必须处理块类型和顺序；Chat Completions 的独立 tool 角色容易接入现有消息存储，代价是参数需要再次 JSON 解析，错误结构也要自己统一。这些是接口形状带来的工程取舍，不代表某家模型必然更可靠。

两边的客户端工具最终都由应用执行，都需要参数验证、权限控制、调用配对和预算限制。本仓库只实现 DeepSeek 的 Chat Completions 适配器；若未来接入其他协议，应转换为统一的内部调用/结果结构，同时保留供应商要求回传的字段，避免把消息简单压成字符串。
